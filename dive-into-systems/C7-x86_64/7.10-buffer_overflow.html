7.10. Real World: Buffer Overflow

C 语言不会自动做数组越界检查。访问数组边界以外的内存是有问题的，常常导致段错误之类的错误。然而，聪明的攻击者可以注入恶意代码，故意越过数组（也称为缓冲区，buffer）的边界，迫使程序以非预期的方式执行。在最坏的情况下，攻击者可以运行代码获得 root 权限，也就是对计算机系统的操作系统级访问权。利用程序中已知的缓冲区越界错误来达到目的的软件，称为缓冲区溢出攻击（buffer overflow exploit）。

The C language does not perform automatic array bounds checking. Accessing memory outside of the bounds of an array is problematic and often results in errors such as segmentation faults. However, a clever attacker can inject malicious code that intentionally overruns the boundary of an array (also known as a buffer) to force the program to execute in an unintended manner. In the worst cases, the attacker can run code that allows them to gain root privilege, or OS-level access to the computer system. A piece of software that takes advantage of the existence of a known buffer overrun error in a program is known as a buffer overflow exploit.

本节我们使用 GDB 和汇编语言，完整剖析缓冲区溢出攻击的机制。阅读本章之前，建议先看看讲解用 GDB 检查汇编代码的那一章。

In this section, we use GDB and assembly language to fully characterize the mechanics of a buffer overflow exploit. Prior to reading this chapter we encourage you to explore the chapter discussing GDB for inspecting assembly code.

7.10.1. 著名的缓冲区溢出案例

7.10.1. Famous Examples of Buffer Overflow

缓冲区溢出攻击出现于 20 世纪 80 年代，直到 21 世纪头几年一直是计算机行业的头号祸害。虽然许多现代操作系统已经能防御最简单的缓冲区溢出攻击，但粗心的编程错误仍然可能让现代程序门户大开。最近在 Skype1、Android2、Google Chrome3 等软件中都发现过缓冲区溢出漏洞。

Buffer overflow exploits emerged in the 1980s and remained a chief scourge of the computing industry through the early parts of the 2000s. While many modern operating systems have protections against the simplest buffer overflow attacks, careless programming errors can still leave modern programs wide open to attack. Buffer overflow exploits have recently been discovered in Skype1, Android2, Google Chrome3, and others.

下面是几个著名的历史案例。

Here are some notable historic examples of buffer overflow exploits.

  • 莫里斯蠕虫（The Morris Worm）

    莫里斯蠕虫4于 1988 年从 MIT 释放到 ARPANet 上（为的是掩盖它出自康奈尔大学一名学生之手），它利用了 UNIX finger 守护进程（fingerd）中的一个缓冲区越界漏洞。在 Linux 和其他类 UNIX 系统中，守护进程（daemon）是一类在后台持续运行的进程，通常执行清理和监控任务。fingerd 守护进程返回关于某台计算机或某个人的友好报告。最要命的是，这个蠕虫的复制机制会把它多次发送到同一台计算机上，把系统拖到无法使用的地步。尽管作者声称这个蠕虫只是一次无害的智力练习，但复制机制让它极易传播，也很难清除。此后多年，还有其他蠕虫利用缓冲区溢出攻击未经授权进入系统，著名的有 Code Red（2001）、MS-SQLSlammer（2003）和 W32/Blaster（2003）。

  • The Morris Worm

    The Morris Worm4 was released in 1988 on ARPANet from MIT (to hide that it was written by a student at Cornell) and exploited a buffer overrun vulnerability that existed in the UNIX finger daemon (fingerd). In Linux and other UNIX-like systems, a daemon is a type of process that continuously executes in the background, usually performing clean-up and monitoring tasks. The fingerd daemon returns a user-friendly report on a computer or person. Most crucially, the worm had a replication mechanism that caused it to be sent to the same computer multiple times, bogging down the system to an unusable state. Although the author claimed that the worm was meant as a harmless intellectual exercise, the replication mechanism enabled the worm to spread easily and made it difficult to remove. In future years, other worms would employ buffer overflow exploits to gain unauthorized access into systems. Notable examples include Code Red (2001), MS-SQLSlammer (2003), and W32/Blaster (2003).

  • AOL 聊天大战（AOL Chat Wars）

    前微软工程师 David Auerbach5 详细讲述了他在 20 世纪 90 年代末把微软的 Messenger Service（MMS）与 AOL Instant Messenger 打通时遭遇的一次缓冲区溢出。那时，想和亲友即时通信（IM），AOL Instant Messenger（AIM）是不二之选。微软想在这个市场站稳脚跟，就在 MMS 中设计了一个功能，让 MMS 用户能和他们的 AIM「好友」聊天。AOL 很不高兴，给服务器打了补丁，让 MMS 无法再连上。微软工程师想出办法让 MMS 客户端模仿 AIM 客户端发给 AOL 服务器的消息，使 AOL 难以区分消息来自 MMS 还是 AIM。AOL 的回应是改变 AIM 发送消息的方式，MMS 工程师则相应地修改客户端消息，使之再次与 AIM 的一致。这场「聊天大战」一直持续，直到 AOL 开始利用自家客户端里的一个缓冲区溢出错误来验证发来的消息是否来自 AIM 客户端。由于 MMS 客户端没有同样的漏洞，聊天大战就此结束，AOL 获胜。

  • AOL Chat Wars

    David Auerbach5, a former Microsoft engineer, detailed his experience with a buffer overflow during his efforts to integrate Microsoft’s Messenger Service (MMS) with AOL Instant Messenger in the late 1990s. Back then, AOL Instant Messenger (AIM) was the service to use if you wanted to instant message (or IM) friends and family. Microsoft tried to gain a foothold in this market by designing a feature in MMS that enabled MMS users to talk to their AIM “buddies.” Displeased, AOL patched their servers so that MMS could no longer connect to them. Microsoft engineers figured out a way for MMS clients to mimic the messages sent by AIM clients to AOL servers, making it difficult for AOL to distinguish between messages received by MMS and AIM. AOL responded by changing the way AIM sent messages, and MMS engineers duly changed their client’s messages to once again match AIM’s. This “chat war” continued until AOL started using a buffer overflow error in their own client to verify that sent messages came from AIM clients. Since MMS clients did not have the same vulnerability, the chat wars ended, with AOL as the victor.

7.10.6. 防御缓冲区溢出

7.10.6. Protecting Against Buffer Overflow

我们展示的例子改变了 secret 可执行文件的控制流，迫使它返回表示成功的零值。然而，这样的攻击可能造成真正的破坏。此外，一些较老的计算机系统会执行栈内存中的字节。如果攻击者把汇编指令对应的字节放到调用栈上，CPU 就会把这些字节当作真正的指令来解释，攻击者就能迫使 CPU 执行任意由他选定的代码。幸运的是，现代计算机系统采用了一些策略，让攻击者更难实施缓冲区溢出攻击：

The example we showed changed the control flow of the secret executable, forcing it to return a zero value associated with success. However, an exploit like this could do some real damage. Furthermore, some older computer systems executed bytes from stack memory. If an attacker placed bytes associated with assembly instructions on the call stack, the CPU would interpret the bytes as real instructions, enabling the attacker to force the CPU to execute any arbitrary code of their choosing. Fortunately, there are strategies that modern computer systems employ to make it more difficult for attackers to run buffer overflow exploits:

  • 栈随机化（stack randomization）：操作系统把栈的起始地址分配在栈内存中的随机位置，使调用栈的位置/大小在程序的每次运行之间都不同。运行同一段代码的多台机器会有不同的栈地址。现代 Linux 系统把栈随机化作为标准做法。然而，执着的攻击者可以用不同的地址反复尝试，暴力破解。一个常见技巧是在真正的攻击代码前面放一个 NOP 滑板（NOP sled，即大量 nop 指令）。执行 nop 指令（0x90）除了让程序计数器递增到下一条指令以外没有任何效果。只要攻击者能让 CPU 从 NOP 滑板中的某处开始执行，NOP 滑板最终就会滑到紧随其后的攻击代码。Aleph One 的文章 Smashing the Stack for Fun and Profit6 详细介绍了这类攻击的机制。
  • Stack randomization: The OS allocates the starting address of the stack at a random location in stack memory, causing the position/size of the call stack to vary from one run of a program to another. Multiple machines running the same code would have different stack addresses. Modern Linux systems use stack randomization as a standard practice. However, a determined attacker can brute force the attack, by attempting to repeat attacks with different addresses. A common trick is to use a NOP sled (i.e., a large number of nop instructions) before the actual exploit code. Executing the nop instruction (0x90) has no effect, other than causing the program counter to increment to the next instruction. As long as the attacker can get the CPU to execute somewhere in the NOP sled, the NOP sled will eventually lead to the exploit code that follows it. Aleph One’s writeup, Smashing the Stack for Fun and Profit6 details the mechanism of this type of attack.

译注

栈随机化是地址空间布局随机化（ASLR，Address Space Layout Randomization）的一部分：现代系统同样会随机化堆、共享库的位置，若程序编译为位置无关可执行文件（PIE），连代码段的位置也会随机化。

  • 栈破坏检测（stack corruption detection）：另一道防线是设法检测栈何时被破坏。较新版本的 GCC 使用一种叫作金丝雀（canary）的栈保护机制，它充当缓冲区与栈上其他元素之间的守卫。金丝雀是存放在不可写内存区域中的一个值，可以与放在栈上的值进行比较。如果金丝雀在程序执行期间「死掉了」，程序就知道自己受到了攻击，并以一条错误信息中止。不过，聪明的攻击者可以替换金丝雀，让程序检测不到栈的破坏。
  • Stack corruption detection: Another line of defense is to try to detect when the stack is corrupted. Recent versions of GCC use a stack protector known as a canary that acts as a guard between the buffer and the other elements of the stack. A canary is a value stored in a nonwriteable section of memory that can be compared to a value put on the stack. If the canary “dies” during a program’s execution, the program knows that it is under attack and aborts with an error message. A clever attacker can, however, replace the canary to prevent the program from detecting stack corruption.

译注 · 金丝雀实际放在哪

在 x86-64 Linux 上，金丝雀的参考值存放在线程局部存储中，用 %fs 段寄存器访问。译者用 clang -target x86_64-linux-gnu -O1 -fstack-protector-strong -S 编译一个带局部数组的函数，可以看到函数开头 movq %fs:40, %rax 取出金丝雀并放到栈上，返回前再与 %fs:40 比较，不一致就调用 __stack_chk_fail 中止程序。GCC 的 -fstack-protector、-fstack-protector-strong、-fstack-protector-all 选项控制哪些函数插入这种检查。

  • 限制可执行区域：这道防线把可执行代码限制在内存中特定的区域。换句话说，调用栈不再是可执行的。然而，就连这种防御也可以被攻破。在利用面向返回编程（return-oriented programming，ROP）的攻击中，攻击者可以从可执行区域中「挑选」指令，从一条指令跳到另一条指令，拼凑出攻击代码。网上有一些著名的例子，尤其是在电子游戏中7。
  • Limiting executable regions: In this line of defense, executable code is restricted to only particular regions of memory. In other words, the call stack is no longer executable. However, even this defense can be defeated. In an attack utilizing return-oriented programming (ROP), an attacker can “cherry-pick” instructions in executable regions and jump from instruction to instruction to build an exploit. There are some famous examples of this online, especially in video games7.

现代更新（截至 2026-11）· 硬件影子栈

针对覆盖返回地址和 ROP 这类攻击，x86 处理器的 CET（Control-flow Enforcement Technology，控制流强制技术）提供了影子栈（shadow stack）：执行 call 时，处理器把返回地址同时压入普通栈和一个应用程序无法直接修改的影子栈；函数返回时比较两份副本，不一致就触发异常。本节那种改写栈上返回地址的攻击，在启用影子栈的程序里会被硬件直接拦下。Linux 内核在 6.6 版（2023 年 10 月）加入了对用户态 x86 影子栈的支持，程序需要由工具链和加载器（如 glibc）配合启用。Linux 内核文档：CET Shadow Stack；Kernel Newbies：Linux 6.6

然而，最好的防线永远是程序员自己。要防止程序遭受缓冲区溢出攻击，尽可能使用带长度说明（length specifier）的 C 函数，并添加执行数组边界检查的代码。至关重要的是，定义的数组必须与选定的长度说明相匹配。表 1 列出了一些容易受缓冲区溢出影响的「坏」C 函数，以及对应应当使用的「好」函数（假设 buf 分配了 12 个字节）。

However, the best line of defense is always the programmer. To prevent buffer overflow attacks on your programs, use C functions with length specifiers whenever possible and add code that performs array bounds checking. It is crucial that any defined arrays match the chosen length specifiers. Table 1 lists some common “bad” C functions that are vulnerable to buffer overflow and the corresponding “good” function to use (assume that buf is allocated 12 bytes).

strcat(buf2, buf) strncat(buf2, buf, 12)
sprintf(buf, "%d", num) snprintf(buf, 12, "%d", num)
Instead of: Use:
gets(buf) fgets(buf, 12, stdin)
scanf("%s", buf) scanf("%12s", buf)
strcpy(buf2, buf) strncpy(buf2, buf, 12)

译注 · 表中有两处仍会溢出

  • **scanf("%12s", buf) 应为 %11s**：%s 的宽度只限制读入的字符数，scanf 还要在后面再写一个 '\0'，所以 %12s 最多写 13 字节，对 12 字节的 buf 正好越界 1 字节。译者用 clang 编译这一行，会得到警告：'scanf' may overflow; destination buffer in argument 2 has size 12, but the corresponding specifier may require size 13。fgets(buf, 12, stdin) 和 snprintf(buf, 12, ...) 的 12 则是包含 '\0' 在内的缓冲区总大小，是对的。
  • strncat 的第三个参数不是目标缓冲区的大小，而是最多从源串追加多少个字符；目标缓冲区至少要有 strlen(dst) + strnlen(src, n) + 1 字节（见 strncat(3)）。若 buf2 中已有内容，strncat(buf2, buf, 12) 照样会溢出，安全的上限应是 sizeof(buf2) - strlen(buf2) - 1。
  • strncpy(buf2, buf, 12) 不会溢出，但当 buf 的长度不小于 12 时，它不会写入 '\0'，buf2 将不是一个合法的字符串（参见第 2 章关于字符串函数的译注）。
