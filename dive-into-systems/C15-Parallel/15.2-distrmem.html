15.2. Distributed Memory Systems, Message Passing, and MPI

第 14 章介绍了 Pthreads 和 OpenMP 等机制，程序可以借助它们在共享内存系统上利用多个 CPU 核心。在这类系统中，所有核心共享同一套物理内存硬件，因此它们可以通过读写共享的内存地址来交换数据、同步各自的行为。虽然共享内存系统让通信变得相对容易，但其可扩展性受限于系统中 CPU 核心的数量。

Chapter 14 describes mechanisms like Pthreads and OpenMP that programs use to take advantage of multiple CPU cores on a shared memory system. In such systems, each core shares the same physical memory hardware, allowing them to communicate data and synchronize their behavior by reading from and writing to shared memory addresses. Although shared memory systems make communication relatively easy, their scalability is limited by the number of CPU cores in the system.

截至 2019 年，高端商用服务器 CPU 一般最多提供 64 个核心。然而对于某些任务来说，即便有几百个 CPU 核心也远远不够。例如，设想模拟地球海洋的流体动力学，或者为整个万维网的内容建立索引以构建一个搜索应用。这类庞大的任务所需的物理内存和处理器数量，超出了任何一台计算机所能提供的范围。因此，需要大量 CPU 核心的应用会运行在放弃了共享内存的系统上：它们运行在由多台计算机组成的系统中，每台计算机都有自己的 CPU 和内存，彼此通过网络通信来协调行为。

As of 2019, high-end commercial server CPUs generally provide a maximum of 64 cores. For some tasks, though, even a few hundred CPU cores isn’t close enough. For example, imagine trying to simulate the fluid dynamics of the Earth’s oceans or index the entire contents of the World Wide Web to build a search application. Such massive tasks require more physical memory and processors than any single computer can provide. Thus, applications that require a large number of CPU cores run on systems that forego shared memory. Instead, they execute on systems built from multiple computers, each with their own CPU(s) and memory, that communicate over a network to coordinate their behavior.

现代更新（截至 2026-11）· 核数早已不止 64

  • AMD 第 6 代 EPYC（Venice，Zen 6）：AMD 公布的 2026 年产品，最多 256 核。Tom’s Hardware

一组协同工作的计算机被称为分布式内存系统（distributed memory system，通常也直接叫分布式系统）。

A collection of computers working together is known as a distributed memory system (or often just distributed system).

原书注 · 关于时间顺序的说明（A Note on Chronology）

虽然本书按这样的顺序来介绍，但实际上，早在线程或 OpenMP 这类机制出现之前，系统设计者就已经在构建分布式系统了。

Despite the order in which they’re presented in this book, systems designers built distributed systems long before mechanisms like threads or OpenMP existed.

有些分布式内存系统的硬件集成度比其他系统更高。例如，超级计算机是一种高性能系统，其中大量计算节点紧密耦合（高度集成）在一个高速互连网络上。每个计算节点都有自己的 CPU、GPU 和内存，但多个节点可能共享二级存储、电源等辅助资源。不同超级计算机之间，硬件共享的具体程度各不相同。

Some distributed memory systems integrate hardware more closely than others. For example, a supercomputer is a high-performance system in which many compute nodes are tightly coupled (closely integrated) to a fast interconnection network. Each compute node contains its own CPU(s), GPU(s), and memory, but multiple nodes might share auxiliary resources like secondary storage and power supplies. The exact level of hardware sharing varies from one supercomputer to another.

在另一个极端，分布式应用可能运行在一组松散耦合（集成度较低）、完全自治的计算机（节点）上，这些节点通过以太网等传统局域网（LAN）技术相连。这样的一组节点被称为商用现成（commodity off-the-shelf，COTS）集群。COTS 集群通常采用无共享架构（shared-nothing architecture），即每个节点都拥有自己的一整套计算硬件（CPU、GPU、内存和存储）。图 1 展示了一个由两台共享内存计算机组成的无共享分布式系统。

On the other end of the spectrum, a distributed application might run on a loosely coupled (less integrated) collection of fully autonomous computers (nodes) connected by a traditional local area network (LAN) technology like Ethernet. Such a collection of nodes is known as a commodity off-the-shelf (COTS) cluster. COTS clusters typically employ a shared-nothing architecture in which each node contains its own set of computation hardware (CPU(s), GPU(s), memory, and storage). Figure 1 illustrates a shared-nothing distributed system consisting of two shared-memory computers.

15.2.1. 并行与分布式处理模型

15.2.1. Parallel and Distributed Processing Models

应用设计者通常会采用一些久经考验的设计来组织分布式应用。采用这样的应用模型有助于开发者推理应用的行为，因为应用的行为会遵循大家熟知的规范。每种模型都有自己独特的优缺点——不存在放之四海而皆准的方案。下面我们简要介绍几种较常见的模型，但请注意，这并不是一份详尽的清单。

Application designers often organize distributed applications using tried-and-true designs. Adopting application models like these helps developers reason about an application because its behavior will conform to well-understood norms. Each model has its unique benefits and drawbacks — there’s no one-size-fits-all solution. We briefly characterize a few of the more common models below, but note that we’re not presenting an exhaustive list.

客户端/服务器

Client/Server

客户端/服务器模型（client/server model）是一种极其常见的应用模型，它把应用的职责划分给两类参与者：客户端进程和服务器进程。服务器进程为请求完成某项工作的客户端提供服务。服务器进程通常在一个众所周知的地址上等待，接收来自客户端的连接。建立连接后，客户端向服务器进程发送请求，服务器要么满足这些请求（例如取回所请求的文件），要么报告错误（例如文件不存在，或客户端无法通过身份验证）。

The client/server model is an extremely common application model that divides an application’s responsibilities among two actors: client processes and server processes. A server process provides a service to clients that ask for something to be done. Server processes typically wait at well-known addresses to receive incoming connections from clients. Upon making a connection, a client sends requests to the server process, which either satisfies those requests (e.g., by fetching a requested file) or reports an error (e.g., the file not existing or the client can’t be properly authenticated).

你可能没有意识到，你正在阅读的这本教科书就是通过客户端/服务器模型访问的！你的 Web 浏览器（客户端）连接到一个位于公共地址（diveintosystems.org）的网站（服务器），以获取本书的内容。

Although you may not have considered it, you accessed the textbook you’re reading right now via the client/server model! Your web browser (client) connected to a website (server) at a public address (diveintosystems.org) to retrieve the book’s contents.

流水线

Pipeline

流水线模型（pipeline model）把应用划分为一系列不同的步骤，数据从一个步骤流向下一个步骤。流水线中的各个组件独立且同时地处理各自的数据。这种模型很适合这样的应用：其工作流程是对大量输入数据执行线性的、重复性的任务。例如，考虑计算机动画电影的制作。电影的每一帧都必须经过一系列步骤的处理来变换画面（例如添加纹理或施加光照）。由于每个步骤都在序列中独立进行，动画师可以在一个大型计算机集群上并行处理多个帧，从而加快渲染速度。

The pipeline model divides an application into a distinct sequence of steps in which data flows from one step to another. Individual components within the pipeline each process their data independently and simultaneously. This model works well for applications whose workflow involves linear, repetitive tasks over large data inputs. For example, consider the production of computer-animated films. Each frame of the film must be processed through a sequence of steps that transform the frame (e.g., adding textures or applying lighting). Because each step happens independently in a sequence, animators can speed up rendering by processing frames in parallel across a large cluster of computers.

主管/工人（Boss/Worker）

Boss/Worker

在主管/工人模型（boss/worker model）中，一个进程充当中央协调者，把工作分配给其他节点上的进程。这种模型适合需要处理大量可分割输入的问题。boss 把输入分成较小的片段，给每个 worker 分配一个或多个片段。在一些应用中，boss 可能会静态地给每个 worker 恰好分配一个输入片段；而在另一些应用中，worker 可能会反复地处理完一个输入片段后，再回到 boss 那里动态地领取下一块输入。本节稍后会展示一个示例程序，其中 boss 把一个数组分给许多 worker，对数组执行标量乘法。

In the boss/worker model, one process acts as a central coordinator and distributes work among the processes at other nodes. This model works well for problems that require processing a large, divisible input. The boss divides the input into smaller pieces and assigns one or more pieces to each worker. In some applications, the boss might statically assign each worker exactly one piece of the input. In other cases, the workers might repeatedly finish a piece of the input and then return to the boss to dynamically retrieve the next input chunk. Later in this section, we’ll present an example program in which a boss divides an array among many workers to perform scalar multiplication on an array.

译注

静态分配 vs. 动态领取，对应第 14 章 OpenMP 中 schedule(static) 与 schedule(dynamic) 的区别：前者开销小，后者在各块工作量不均衡时能做负载均衡。分布式框架里常见的”任务队列 + 工作者拉取任务”（如 Celery、Ray、Spark 的任务调度）都是动态领取的变体。

注意，这种模型有时也被称为其他名字，比如”master/worker”（主/从）或其他变体，但核心思想是一样的。

Note that this model is sometimes called other names, like “master/worker” or other variants, but the main idea is the same.

对等（Peer-to-Peer）

Peer-to-Peer

与主管/工人模型不同，对等（peer-to-peer，P2P）应用不依赖于一个中央控制进程。相反，各个对等进程会自行把应用组织成一种结构，在其中它们各自承担大致相同的职责。例如，在 BitTorrent 文件共享协议中，每个对等节点反复与其他节点交换文件的各个部分，直到所有节点都收到了完整的文件。

Unlike the boss/worker model, a peer-to-peer application avoids relying on a centralized control process. Instead, peer processes self-organize the application into a structure in which they each take on roughly the same responsibilities. For example, in the BitTorrent file sharing protocol, each peer repeatedly exchanges parts of a file with others until they’ve all received the entire file.

由于没有中心化组件，对等应用通常对节点故障具有较强的鲁棒性。另一方面，对等应用通常需要复杂的协调算法，这使得它们难以构建，也难以进行严格的测试。

Lacking a centralized component, peer-to-peer applications are generally robust to node failures. On the other hand, peer-to-peer applications typically require complex coordination algorithms, making them difficult to build and rigorously test.

15.2.2. 通信协议

15.2.2. Communication Protocols

无论是作为超级计算机的一部分，还是 COTS 集群的一部分，分布式内存系统中的进程都通过消息传递（message passing）进行通信：一个进程显式地向一个或多个其他节点上的进程发送消息，由它们接收。如何利用网络由运行在系统上的应用自己决定——有些应用需要频繁通信，以便紧密协调许多节点上进程的行为；而另一些应用通信只是为了把大量输入分给各个进程，之后基本上独立工作。

Whether they are part of a supercomputer or a COTS cluster, processes in a distributed memory system communicate via message passing, whereby one process explicitly sends a message to processes on one or more other nodes, which receive it. It’s up to the applications running on the system to determine how to utilize the network — some applications require frequent communication to tightly coordinate the behavior of processes across many nodes, whereas other applications communicate to divide up a large input among processes and then mostly work independently.

分布式应用通过定义一个通信协议（protocol）来正式规定它的通信方式。协议描述了一组管理应用如何使用网络的规则，包括：

A distributed application formalizes its communication expectations by defining a communication protocol, which describes a set of rules that govern its use of the network, including:

  • 进程应该在什么时候发送消息
  • When a process should send a message
  • 应该把消息发给哪个（些）进程
  • To which process(es) it should send the message
  • 消息应该采用什么格式
  • How to format the message

没有协议，应用可能无法正确地解读消息，甚至可能发生死锁。例如，如果一个应用由两个进程组成，而每个进程都在等待对方先给自己发消息，那么两个进程都永远无法继续推进。协议为通信增加了结构，降低了出现这类故障的可能性。

Without a protocol, an application might fail to interpret messages properly or even deadlock. For example, if an application consists of two processes, and each process waits for the other to send it a message, neither process will ever make progress. Protocols add structure to communication to reduce the likelihood of such failures.

为了实现通信协议，应用需要一些基本功能，比如发送和接收消息、为进程命名（寻址）以及同步进程的执行。许多应用借助消息传递接口（Message Passing Interface）来获得这些功能。

To implement a communication protocol, applications require basic functionality for tasks like sending and receiving messages, naming processes (addressing), and synchronizing process execution. Many applications look to the Message Passing Interface for such functionality.

15.2.3. 消息传递接口（MPI）

15.2.3. Message Passing Interface (MPI)

消息传递接口（Message Passing Interface，MPI）定义了（但本身并不实现）一套标准化的接口，应用可以用它在分布式内存系统中进行通信。通过采用 MPI 通信标准，应用就具备了可移植性（portable），也就是说，它们可以在许多不同的系统上编译和运行。换句话说，只要系统上安装了某个 MPI 实现，一个可移植的应用就可以从一个系统迁移到另一个系统，并且可以期望它正确执行，即使这些系统的底层特性各不相同。

The Message Passing Interface (MPI) defines (but does not itself implement) a standardized interface that applications can use to communicate in a distributed memory system. By adopting the MPI communication standard, applications become portable, meaning that they can be compiled and executed on many different systems. In other words, as long as an MPI implementation is installed, a portable application can move from one system to another and expect to execute properly, even if the systems have different underlying characteristics.

现代更新（截至 2026-11）· MPI 标准版本

MPI-4.0（2021-06-09）→ MPI-4.1（2023-11-02）→ MPI-5.0（2025-06-05）。MPI Forum MPI-5.0 最大的变化是加入标准 ABI，让不同厂商的 MPI 实现在二进制层面可以互换（以前用 Open MPI 编译的程序不能直接换 MPICH 运行）；任何合法的 MPI-4.1 程序仍是合法的 MPI-5.0 程序，本节示例代码不受影响。MPI-5.0 背景说明

MPI 允许程序员把一个应用划分成多个进程。它给应用中的每个进程分配一个唯一的标识符，称为 rank（秩，即进程编号）。对于一个有 N 个进程的应用，rank 的取值范围是 0 到 N-1。进程可以调用 MPI_Comm_rank 函数得知自己的 rank，调用 MPI_Comm_size 得知应用中一共有多少个进程在执行。要发送消息，进程调用 MPI_Send 并指定目标接收者的 rank。类似地，进程调用 MPI_Recv 来接收消息，并指定是等待来自某个特定节点的消息，还是接收来自任意发送者的消息（使用常量 MPI_ANY_SOURCE 作为 rank）。

MPI allows a programmer to divide an application into multiple processes. It assigns each of an application’s processes a unique identifier, known as a rank, which ranges from 0 to N-1 for an application with N processes. A process can learn its rank by calling the MPI_Comm_rank function, and it can learn how many processes are executing in the application by calling MPI_Comm_size. To send a message, a process calls MPI_Send and specifies the rank of the intended recipient. Similarly, a process calls MPI_Recv to receive a message, and it specifies whether to wait for a message from a specific node or to receive a message from any sender (using the constant MPI_ANY_SOURCE as the rank).

除了基本的发送和接收函数之外，MPI 还定义了多种函数，使一个进程更容易把数据传给多个接收者。例如，MPI_Bcast 允许一个进程只调用一次函数，就把一条消息发送给应用中的所有其他进程。MPI 还定义了一对函数 MPI_Scatter 和 MPI_Gather：一个进程可以把数组拆分开，把各个片段分发给各个进程（scatter，分发），各进程处理完数据后，再把所有数据取回来汇总结果（gather，收集）。

In addition to the basic send and receive functions, MPI also defines a variety of functions that make it easier for one process to communicate data to multiple recipients. For example, MPI_Bcast allows one process to send a message to every other process in the application with just one function call. It also defines a pair of functions, MPI_Scatter and MPI_Gather, that allow one process to divide up an array and distribute the pieces among processes (scatter), operate on the data, and then later retrieve all the data to coalesce the results (gather).

译注 · 集合通信（collective communication）

Bcast / Scatter / Gather 这类”一组进程一起参与”的操作统称集合通信。另外两个必须认识的是 **MPI_Reduce**（把各进程的值用加法/求最大值等运算归约到一个进程）和 MPI_Allreduce（归约后结果发回给所有进程）。Allreduce 今天最出名的用途是分布式深度学习训练：每块 GPU 算出自己那份数据的梯度后，用 all-reduce 求和/平均，再各自更新模型参数——这就是数据并行训练的核心一步。

现代更新 · 集合通信与 AI

NVIDIA 的 NCCL 库为多 GPU 提供 AllReduce、Broadcast、Reduce、AllGather、ReduceScatter、AlltoAll、Gather、Scatter 等集合操作，名字与 MPI 一一对应；数据并行训练每一步都要用 AllReduce 汇总各 GPU 的梯度。NCCL 文档

由于 MPI 只规定了一组函数及其应有的行为，每个系统的设计者都可以根据自己系统的能力，以合适的方式来实现 MPI 的功能。例如，如果一个系统的互连网络支持广播（同时把一条消息的一份拷贝发送给多个接收者），那么它实现 MPI 的 MPI_Bcast 函数的效率，可能会比不支持广播的系统更高。

Because MPI specifies only a set of functions and how they should behave, each system designer can implement MPI’s functionality in a way that matches the capabilities of their particular system. For example, a system with an interconnect network that supports broadcasting (sending one copy of a message to multiple recipients at the same time) might be able to implement MPI’s MPI_Bcast function more efficiently than a system without such support.

在这段代码中，boss 执行一个循环，每个 worker 进程执行一次，每次给一个 worker 发送数组的一个片段。它从 array 地址偏移 (i * local_size) 的位置开始发送数据，以确保每个 worker 拿到的是数组中独有的一段。也就是说，rank 1 的 worker 拿到从下标 5 开始的一段，rank 2 拿到从下标 10 开始的一段，依此类推，如图 2 所示。

In this code, the boss executes a loop that executes once for each worker process, in which it sends the worker a piece of the array. It starts sending data from the address of array at an offset of (i * local_size) to ensure that each worker gets a unique piece of the array. That is, the worker with rank 1 gets a piece of the array starting at index 5, rank 2 gets a piece of the array starting at index 10, etc., as shown in Figure 2.

每次调用 MPI_Send 都会把 local_size（5）个整数的数据（20 字节）发送给 rank 为 i 的进程。靠近末尾的参数 0 表示消息标签（tag），这是一个本程序用不到的高级特性——把它设为 0 就是对所有消息一视同仁。

Each call to MPI_Send sends local_size (5) integers worth of data (20 bytes) to the process with rank i. The 0 argument toward the end represents a message tag, which is an advanced feature that this program doesn’t need — setting it to 0 treats all messages equally.

所有 worker 都调用 MPI_Recv 来获取属于自己的数组片段，并把它存放到 local_array 所指向的内存地址中。它们从 rank 为 0 的节点接收 local_size（5）个整数的数据（20 字节）。注意，MPI_Recv 是一个阻塞（blocking）调用，也就是说，调用它的进程会暂停，直到收到数据为止。由于 MPI_Recv 调用会阻塞，在 boss 发来属于自己的数组片段之前，任何 worker 都不会继续往下执行。

The workers all call MPI_Recv to retrieve their piece of the array, which they store in memory at the address to which local_array refers. They receive local_size (5) integers worth of data (20 bytes) from the node with rank 0. Note that MPI_Recv is a blocking call, which means that a process that calls it will pause until it receives data. Because the MPI_Recv call blocks, no worker will proceed until the boss sends its piece of the array.

译注 · MPI_Send 会不会阻塞？

MPI_Send（标准模式）的语义是”返回后发送缓冲区可以安全复用”，它可能阻塞到对方开始接收，也可能先把小消息拷进内部缓冲区立即返回——这取决于实现和消息大小。所以”两个进程都先 Send 再 Recv”的代码，消息小时能跑通、消息一大就死锁，这是 MPI 初学者最经典的 bug。解决办法：调整收发顺序、用 MPI_Sendrecv，或改用非阻塞的 MPI_Isend / MPI_Irecv 再配合 MPI_Wait（非阻塞通信还能让计算与通信重叠）。

分发/收集（Scatter/Gather）

Scatter/Gather

虽然上一个例子中的 for 循环用 MPI_Send 和 MPI_Recv 正确地分发了数据，但它们没有简洁地表达出背后的意图。也就是说，在 MPI 看来，它们只是一连串的发送和接收调用，看不出”把一个数组分发到各个 MPI 进程”这个明显的目标。由于并行应用经常需要像这个示例数组一样分发和收集数据，MPI 专门为此提供了函数：MPI_Scatter 和 MPI_Gather。

Although the for loops in the previous example correctly distribute data with MPI_Send and MPI_Recv, they don’t succinctly capture the intent behind them. That is, they appear to MPI as a series of send and receive calls without the obvious goal of distributing an array across MPI processes. Because parallel applications frequently need to distribute and collect data like this example array, MPI provides functions for exactly this purpose: MPI_Scatter and MPI_Gather.

15.2.6. 分布式系统面临的挑战

15.2.6. Distributed Systems Challenges

一般来说，协调分布式系统中多个进程的行为是出了名的困难。在共享内存系统中，如果某个硬件部件（例如 CPU 或电源）发生故障，整个系统都会无法工作。但在分布式系统中，各个自治的节点可能会独立地发生故障。例如，如果一个节点消失了而其他节点仍在运行，应用必须决定接下来该怎么办。类似地，互连网络也可能发生故障，这时在每个进程看来，就好像其他所有进程都失效了一样。

In general, coordinating the behavior of multiple processes in distributed systems is notoriously difficult. If a hardware component (e.g., CPU or power supply) fails in a shared memory system, the entire system becomes inoperable. In a distributed system though, autonomous nodes can fail independently. For example, an application must decide how to proceed if one node disappears and the others are still running. Similarly, the interconnection network could fail, making it appear to each process as if all the others failed.

译注 · 延伸阅读的关键词

这一段点到的问题，就是分布式系统这门课的核心：部分失效（partial failure）、网络分区（partition，以及由此引出的 CAP 定理），以及在不可靠网络上让多个节点对某个值达成一致的共识算法（Paxos、Raft；etcd、ZooKeeper 等协调服务都建立在它们之上）。经典 MPI 程序对故障的处理很简单粗暴：任何一个进程挂了，整个作业就中止，靠定期写检查点（checkpoint）再重启来恢复。想系统学习，推荐 MIT 6.5840（原 6.824）分布式系统课程和《数据密集型应用系统设计》（DDIA）。

分布式系统还面临着因缺乏共享硬件——即时钟——而带来的挑战。由于网络传输存在不可预测的延迟，自治的节点很难确定消息发送的先后顺序。解决这些挑战（以及其他许多挑战）超出了本书的范围。幸运的是，分布式软件的设计者已经构建了若干框架，让分布式应用的开发变得更容易。我们将在下一节介绍其中的一些框架。

Distributed systems also face challenges due to a lack of shared hardware, namely clocks. Due to unpredictable delays in network transmission, autonomous nodes cannot easily determine the order in which messages are sent. Solving these challenges (and many others) is beyond the scope of this book. Fortunately, distributed software designers have constructed several frameworks that ease the development of distributed applications. We characterize some of these frameworks in the next section.

译注

关于”没有共享时钟”：经典解法是 Lamport 在 1978 年提出的逻辑时钟（只关心事件的因果先后，不关心物理时间），以及后来的向量时钟；工程上则有 NTP/PTP 时钟同步，Google Spanner 的 TrueTime 更进一步，用 GPS 和原子钟把时钟误差限定在一个已知区间内，再通过”等待误差区间过去”来保证全局顺序。
