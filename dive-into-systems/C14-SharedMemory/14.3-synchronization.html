14.3. Synchronizing Threads

在我们迄今看过的例子中，每个线程在执行时都不与其他任何线程共享数据。例如，在标量乘法程序中，数组的每个元素都完全独立于其他所有元素，因此线程之间无须共享数据。

In the examples we’ve looked at thus far, each thread executes without sharing data with any other threads. In the scalar multiplication program, for instance, each element of the array is entirely independent of all the others, making it unnecessary for the threads to share data.

然而，线程能够方便地与其他线程共享数据，正是它的主要特点之一。回想一下，多线程进程的所有线程共享该进程公共的堆。在本节中，我们详细研究线程可以使用的数据共享和保护机制。

However, a thread’s ability to easily share data with other threads is one of its main features. Recall that all the threads of a multithreaded process share the heap common to the process. In this section, we study the data sharing and protection mechanisms available to threads in detail.

线程同步（thread synchronization）指的是强制线程按特定的顺序执行。尽管同步线程可能会增加程序的运行时间，但为了确保程序的正确性，它常常是必要的。在本节中，我们主要讨论一种同步结构（互斥锁）如何帮助确保多线程程序的正确性。本节最后讨论其他几种常见的同步结构：信号量、屏障和条件变量。

Thread synchronization refers to forcing threads to execute in a particular order. Even though synchronizing threads can add to the runtime of a program, it is often necessary to ensure program correctness. In this section, we primarily discuss how one synchronization construct (a mutex) helps ensure the correctness of a threaded program. We conclude the section with a discussion of some other common synchronization constructs: semaphores, barriers and condition variables.

计数排序（CountSort）

CountSort

我们来研究一个稍微复杂一点的例子：计数排序（CountSort）。计数排序算法是一种简单的线性（O(N)）排序算法，用于对取值范围已知且较小（共 R 种取值，R 远小于 N）的数据进行排序。为了说明计数排序如何工作，考虑一个有 15 个元素的数组 A，其中所有元素都是 0 到 9 之间（10 种可能取值）的随机值：

Let’s study a slightly more complicated example called CountSort. The CountSort algorithm is a simple linear (O(N)) sorting algorithm for sorting a known small range of R values, where R is much smaller than N. To illustrate how CountSort works, consider an array A of 15 elements, all of which contain random values between 0 and 9 (10 possible values):

对于一个特定的数组，计数排序的工作过程如下：

For a particular array, CountSort works as follows:

  1. 统计数组中每个值出现的频次。
  1. It counts the frequency of each value in the array.
  1. 按照每个值的频次逐个列举，覆盖原数组。
  1. It overwrites the original array by enumerating each value by its frequency.

第 1 步之后，每个值的频次被放进一个长度为 10 的 counts 数组中，其中 counts[i] 的值是值 i 在数组 A 中出现的频次。例如，由于数组 A 中有三个值为 2 的元素，所以 counts[2] 为 3。

After step 1, the frequency of each value is placed in a counts array of length 10, where the value of counts[i] is the frequency of the value i in array A. For example, since there are three elements with value 2 in array A, counts[2] is 3.

数据竞争

Data Races

为了弄清发生了什么，我们考虑在多核系统的两个不同核心上用两个线程运行的一个例子。回想一下，任何线程的执行都可能随时被操作系统抢占，这意味着在任一时刻，每个线程可能正在执行某个函数的不同指令（也可能是同一条指令）。表 1 展示了经过 countElems 函数的一条可能的执行路径。为了更好地说明发生了什么，我们把 counts[val] = counts[val] + 1 这一行翻译成下面这串等价的指令：

To understand what’s going on, let’s consider an example run with two threads on two separate cores of a multicore system. Recall that the execution of any thread can be preempted at any time by the OS, which means that each thread could be running different instructions of a particular function at any given time (or possibly the same instruction). Table 1 shows one possible path of execution through the countElems function. To better illustrate what is going on, we translated the line counts[val] = counts[val] + 1 into the following sequence of equivalent instructions:

  1. 读取 counts[val]，放入一个寄存器。
  1. Read counts[val] and place into a register.
  1. 修改寄存器，把它加一。
  1. Modify the register by incrementing it by one.
  1. 把寄存器的内容写回 counts[val]。
  1. Write the contents of the register to counts[val].

这称为读-改-写（read-modify-write）模式。在表 1 所示的例子中，每个线程在不同的核心上执行（线程 0 在核心 0 上，线程 1 在核心 1 上）。我们从时间步 i 开始考察进程的执行，此时两个线程的 val 都是 1。

This is known as the read-modify-write pattern. In the example shown in Table 1, each thread executes on a separate core (Thread 0 on Core 0, Thread 1 on Core 1). We start inspecting the execution of the process at time step i, where both threads have a val of 1.

假设在表 1 的执行序列之前，counts[1] 的值为 60。在时间步 i，线程 0 读取 counts[1]，把值 60 放入核心 0 的寄存器。在时间步 i+1，线程 0 把核心 0 的寄存器加一，与此同时，线程 1 把 counts[1] 的当前值（60）读入核心 1 的寄存器。在时间步 i+2，线程 0 用值 61 更新 counts[1]，同时线程 1 把存放在它本地寄存器中的值（60）加一。最终结果是，在时间步 i+3，counts[1] 被线程 1 用值 61 覆盖，而不是我们预期的 62！这实际上让 counts[1]「丢失」了一次加一！

Suppose that, prior to the execution sequence in Table 1, counts[1] contains the value 60. In time step i, Thread 0 reads counts[1] and places the value 60 in Core 0’s register. In time step i+1, while Thread 0 increments Core 0’s register by one, the current value in counts[1] (60) is read into Core 1’s register by Thread 1. In time step i+2, Thread 0 updates counts[1] with the value 61 while Thread 1 increments the value stored in its local register (60) by one. The end result is that during time step i+3, the value counts[1] is overwritten by Thread 1 with the value 61, not 62 as we would expect! This causes counts[1] to essentially “lose” an increment!

我们把两个线程试图写同一个内存位置的情形称为数据竞争（data race）。更一般地说，竞态条件（race condition）指的是两个操作同时执行会得到错误结果的任何情形。注意，同时读取 counts[1] 这个位置本身并不构成竞态条件，因为一般来说，单纯从内存中读取值不会有问题。是这一步与对 counts[1] 的写操作结合在一起，才导致了错误的结果。在大多数多线程程序中，这种读-改-写模式是一种特定类型的竞态条件，即数据竞争的常见来源。在讨论竞态条件及其修正方法时，我们集中讨论数据竞争。

We refer to the scenario in which two threads attempt to write to the same location in memory as a data race condition. More generally, a race condition refers to any scenario in which the simultaneous execution of two operations gives an incorrect result. Note that a simultaneous read of the counts[1] location would not in and of itself constitute a race condition, because values can generally read alone from memory without issue. It was the combination of this step with the writes to counts[1] that caused the incorrect result. This read-modify-write pattern is a common source of a particular type of race condition, called a data race, in most threaded programs. In our discussion of race conditions and how to fix them, we focus on data races.

原书注 · 原子操作（Atomic operations）

如果一个线程感觉某个操作是不间断地执行的（换句话说，是一个「要么全做、要么不做」的动作），这个操作就被定义为原子的（atomic）。在一些库中，会用一个关键字或类型来指明某块计算应当被视为原子的。在前面的例子中，counts[val] = counts[val] + 1 这一行（即使写成 counts[val]++）不是原子的，因为这一行在机器层面实际上对应好几条指令。需要互斥这样的同步结构，才能确保没有数据竞争。一般来说，除非显式地强制互斥，否则应当假定所有操作都是非原子的。

An operation is defined as being atomic if a thread perceives it as executing without interruption (in other words, as an “all or nothing” action). In some libraries, a keyword or type is used to specify that a block of computation should be treated as being atomic. In the previous example, the line counts[val] = counts[val] + 1 (even if written as counts[val]++) is not atomic, because this line actually corresponds to several instructions at the machine level. A synchronization construct like mutual exclusion is needed to ensure that there are no data races. In general, all operations should be assumed to be nonatomic unless mutual exclusion is explicitly enforced.

译注 · 用机器码看「读-改-写」与 C11 原子操作

译者在 Apple Silicon Mac 上用 clang -O2 -S 编译 plain[val] = plain[val] + 1;，得到的正是上文所说的三步：ldr（读）、add（改）、str（写）。C11 起，标准库 <stdatomic.h> 提供了原子类型和原子操作，例如 atomic_fetch_add，它以原子方式把一个值加到原子对象上，相当于一次原子的读-改-写（见 cppreference：atomic_fetch_add）。把 counts 声明为 atomic_long counts[10]; 并改用 atomic_fetch_add(&counts[val], 1); 后，同样的编译得到的是单条 ARMv8.1 原子指令 ldaddal，这类简单的计数器就不再需要互斥锁了。

要修正数据竞争，首先必须把临界区（critical section）隔离出来，即为了确保正确的行为而必须原子地（孤立地）执行的那部分代码。在多线程程序中，更新共享资源的代码块通常被认定为临界区。

To fix a data race, we must first isolate the critical section, or the subset of code that must execute atomically (in isolation) to ensure correct behavior. In threaded programs, blocks of code that update a shared resource are typically identified to be critical sections.
