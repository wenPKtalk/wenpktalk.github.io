12.3. Memory Considerations

程序员应当特别注意内存的使用，尤其是在使用矩阵和数组这类占用大量内存的数据结构时。尽管编译器提供了强大的优化功能，但编译器并不总能做出改善程序内存使用的优化。在本节中，我们用一个矩阵-向量程序的实现（matrixVector.c）来引导对改善内存使用的技术和工具的讨论。

Programmers should pay special attention to memory use, especially when employing memory-intensive data structures such as matrices and arrays. Although compilers offer powerful optimization features, the compiler cannot always make optimizations that improve a program’s memory use. In this section, we use an implementation of a matrix-vector program (matrixVector.c) to guide discussion of techniques and tools for improving memory use.

这个程序的 main 函数执行两个步骤。首先，它分配并初始化输入矩阵、输入向量和输出矩阵。然后，它执行矩阵-向量乘法。在 10,000 × 10,000 的矩阵-向量规模上运行代码，可以看到 matrixVectorMultiply 函数占用了大部分时间：

The main function of the program performs two steps. First, it allocates and initializes the input matrix, the input vector, and the output matrix. Next, it performs matrix-vector multiplication. Running the code on matrix-vector dimensions of 10,000 × 10,000 reveals that the matrixVectorMultiply function takes up the majority of the time:

因此，我们的讨论将集中在 matrixVectorMultiply 函数上。

Our discussion will thus focus on the matrixVectorMultiply function.

12.3.1. 循环交换

12.3.1. Loop Interchange

循环交换（loop interchange）优化交换嵌套循环中内外层循环的顺序，以最大化缓存局部性。编译器很难自动完成这项任务。GCC 中虽然有 -floop-interchange 编译选项，但目前默认不开启。因此，程序员最好留意自己的代码是如何访问数组和矩阵这类复合内存数据结构的。举个例子，我们来仔细看看 matrixVector.c 中的 matrixVectorMultiply 函数：

Loop interchange optimizations switch the order of inner and outer loops in nested loops in order to maximize cache locality. Automatically performing this task is difficult for compilers to do. In GCC, the -floop-interchange compiler flag exists but is currently not available by default. Therefore, it is a good idea for programmers to pay attention to how their code is accessing memory-composite data structures like arrays and matrices. 输入矩阵和输出矩阵是动态分配的（C 语言章节讨论的第二种方法）。因此，矩阵的各行彼此不连续，而每一行中的元素是连续的。当前的循环顺序使程序逐列而不是逐行地遍历矩阵。回想一下，数据是以块而不是元素为单位加载到缓存中的。因此，当访问 res 或 m 中某个数组的元素 x 时，与 x 相邻的元素也会被加载到缓存中。逐「列」遍历矩阵会导致更多的缓存未命中，因为每次访问都迫使缓存加载新的块。表 2 显示，加上优化选项并没有缩短这个函数的运行时间。然而，只要交换一下循环的顺序（如前面的代码示例以及 matrixVector2.c 所示），函数就能快将近八倍，并让编译器能够进行更多的优化。

The input and output matrices are dynamically allocated (second method discussed in C chapter). As a result, the rows in the matrices are not contiguous to one another, whereas the elements in every row are contiguous. The current ordering of the loops causes the program to cycle through each column instead of every row. Recall that data is loaded into cache in blocks not elements. As a result, when an element x in an array in either res or m is accessed, the elements adjacent to x are also loaded into cache. Cycling through every “column” of the matrix causes more cache misses, as the cache is forced to load new blocks with every access. Table 2 shows that adding optimization flags does not decrease the runtime of the function. However, simply switching the order of the loops (as shown in the previous code examples and in matrixVector2.c) makes the function nearly eight times faster and allows the compiler to perform additional optimizations.

把在同一范围上运行的两个循环的内容合并到一个循环中（即循环分裂的逆过程），称为循环融合（loop fusion）。循环分裂和循环融合都是编译器为改善数据局部性而可能执行的优化。面向多核处理器的编译器也可能利用循环分裂或融合，让循环能在多个核心上高效执行。例如，编译器可能用循环分裂把两个循环分配给不同的核心。同样，编译器可能用循环融合把相互依赖的操作合并到循环体中，再把循环迭代的一个子集分配给每个核心（假设各次迭代之间的数据是独立的）。

The process of taking two loops that operate over the same range and combining their contents into a single loop (i.e., the opposite of loop fission) is called loop fusion. Loop fission and fusion are examples of optimizations a compiler might perform to try to improve data locality. Compilers for multicore processors may also use loop fission or fusion to enable loops to execute efficiently on multiple cores. For example, a compiler may use loop fission to assign two loops to different cores. Likewise, a compiler may use loop fusion to combine together dependent operations into the body of the loop and distribute to each core a subset of the loop iterations (assuming data between iterations are independent).

在我们的例子中，手动应用循环分裂并不能直接提高程序性能；填充数组所需的时间几乎没有变化。不过，它可能会让一个更隐蔽的优化显现出来：包含 fillArrayZeros 的那个循环是不必要的。matrixVectorMultiply 函数会给 result 数组中的每个元素赋值，事先把它们全部初始化为零是多余的。

In our case, applying loop fission manually does not directly improve program performance; there is virtually no change in the amount of time required to fill the array. However, it may make clear a more subtle optimization: the loop containing fillArrayZeros is not necessary. The matrixVectorMultiply function assigns values to each element in the result array; a prior initialization to all zeros is unnecessary.

尽管各个数组在内存中并不连续存放，但每个数组都占 10,000 × sizeof(int) 字节，即 40,000 字节。由于总共分配了 20,000 个数组（初始矩阵和结果矩阵各 10,000 个），这相当于 8 亿字节，即大约 762 MB 的空间。用随机数填满 762 MB 的空间，花很多时间也就不难理解了。对于矩阵，内存使用量随输入规模呈平方增长，可能对性能产生很大影响。

Even though each array is stored noncontiguously in memory, each one takes up 10,000 × sizeof(int) bytes, or 40,000 bytes. Because there is a total of 20,000 (10,000 each for the initial matrix and the result matrix) arrays allocated, this corresponds to 800 million bytes, or roughly 762 MB of space. Filling 762 MB with random numbers understandably takes a lot of time. With matrices, memory use increases quadratically with the input size, and can play a large role in performance.

Like the other Valgrind tools we covered in this book (memcheck, cachegrind, and callgrind), massif runs as a wrapper around a program’s executable. massif 工具揭示出，程序 99.96% 的堆内存使用发生在 allocateArray 函数中，总共分配了 8 亿字节，与我们前面粗略估算的结果一致。读者可能会发现，massif 是识别程序中高堆内存使用区域的有用工具，而高堆内存使用往往会拖慢程序。例如，当程序员频繁调用 malloc 而没有在第一个恰当的时机调用 free 时，程序中就会发生内存泄漏（memory leak）。massif 工具对检测这类泄漏非常有用。
