2.9.5. C Libraries: Using, Compiling, and Linking

库（library）实现了一组可供其他程序使用的函数和定义。C 库由两部分组成：

A library implements a collection of functions and definitions that can be used by other programs. A C library consists of two parts:

  1. 库的应用程序编程接口（API），定义在一个或多个头文件（.h 文件）中，打算使用该库的 C 源文件必须包含这些头文件。头文件定义了库向其用户导出的内容。这些定义通常包括库函数的原型，也可能包括类型、常量或全局变量的声明。
  1. The application programming interface (API) to the library, which gets defined in one or more header files (.h files) that must be included in C source code files that plan to use the library. The headers define what the library exports to its users. These definitions usually include library function prototypes, and they may also include type, constant, or global variable declarations.
  1. 库功能的实现，通常以预编译的二进制形式提供给程序，由 gcc 链接（加入）到它生成的二进制可执行文件中。预编译的库代码可能是一个归档文件（libsomelib.a），其中包含若干 .o 文件，可以在编译时静态链接到可执行文件中；也可能是一个共享目标文件（libsomelib.so），可以在运行时动态链接到正在运行的程序中。
  1. The implementation of the library’s functionality, often made available to programs in a precompiled binary format that gets linked (added) into the binary executable created by gcc. Precompiled library code might be in an archive file (libsomelib.a) containing several .o files that can be statically linked into the executable file at compile time. Alternatively, it may consist of a shared object file (libsomelib.so) that can be dynamically linked at runtime into a running program.

例如，C 字符串库实现了一组操作 C 字符串的函数。string.h 头文件定义了它的接口，所以任何想使用字符串库函数的程序都必须 #include <string.h>。C 字符串库的实现是更大的标准 C 库（libc）的一部分，gcc 编译器会自动把 libc 链接到它生成的每个可执行文件中。

For example, the C string library implements a set of functions to manipulate C strings. The string.h header file defines its interface, so any program that wants to use string library functions must #include <string.h>. The implementation of the C string library is part of the larger standard C library (libc) that the gcc compiler automatically links into every executable file it creates.

库的实现由一个或多个模块（.c 文件）组成，还可能包含库实现内部使用的头文件；内部头文件不属于库的 API，但它们是设计良好的模块化库代码的一部分。库的 C 源代码实现通常不会提供给库的用户，而是以预编译的二进制形式提供。这些二进制格式不是可执行程序（不能单独运行），但它们提供了可执行代码，可以在编译时由 gcc 链接（加入）到可执行文件中。

A library’s implementation consists of one or more modules (.c files), and may additionally include header files that are internal to the library implementation; internal header files are not part of the library’s API but are part of well-designed, modular library code. Often the C source code implementation of a library is not exported to the user of the library. Instead, the library is made available in a precompiled binary form. These binary formats are not executable programs (they cannot be run on their own), but they provide executable code that can be linked into (added into) an executable file by gcc at compilation time.

C 程序员可以使用的库非常多。例如，POSIX 线程库（在第 10 章中讨论）使 C 程序可以多线程运行。C 程序员也可以实现和使用自己的库（在下一节中讨论）。大型 C 程序往往会用到许多 C 库，其中一些由 gcc 隐式链接，另一些则需要用 gcc 的 -l 命令行选项显式链接。

There are numerous libraries available for C programmers to use. For example, the POSIX thread library (discussed in Chapter 10) enables multithreaded C programs. C programmers can also implement and use their own libraries (discussed in the next section). Large C programs tend to use many C libraries, some of which gcc links implicitly, whereas others require explicit linking with the -l command line option to gcc.

注意，链接 POSIX 线程库是个特例，不使用 -l 前缀。不过，大多数库都是在 gcc 命令行中用 -l 语法显式链接到可执行文件中的。还要注意，-l 参数中不应写出库文件的完整文件名：库文件的名字类似 libreadline.so 或 libreadline.a，但文件名中的 lib 前缀和 .so 或 .a 后缀都不写。实际的库文件名可能还包含版本号（例如 libreadline.so.8.0），这些版本号也不写在 -l 命令行选项中（-lreadline）。由于不强制用户指定（甚至不需要知道）要链接的库文件的确切名称和位置，gcc 可以自由地在用户的库路径中查找库的最新版本。这也让编译器在一个库同时有共享目标（.so）版本和归档（.a）版本时，可以选择动态链接。如果用户想静态链接库，可以在 gcc 命令行中显式指定静态链接。--static 选项是请求静态链接的一种方法：

Note that linking the POSIX thread library is a special case that does not include the -l prefix. However, most libraries are explicitly linked into the executable using the -l syntax on the gcc command line. Also note that the full name of the library file should not be included in the -l argument to gcc; the library files are named something like libreadline.so or libreadline.a, but the lib prefix and .so or .a suffix of the filenames are not included. The actual library filename may also contain version numbers (e.g. libreadline.so.8.0), which are also not included in the -l command line option (-lreadline). By not forcing the user to specify (or even know) the exact name and location of the library files to link in, gcc is free to find the most recent version of a library in a user’s library path. It also allows the compiler to choose to dynamically link when both a shared object (.so) and an archive (.a) version of a library are available. 编译步骤

Compilation Steps

刻画 C 程序的编译步骤，有助于说明库代码是如何被链接到可执行二进制文件中的。我们先介绍编译步骤，再（结合例子）讨论编译使用库的程序时可能出现的各类错误。

Characterizing C’s program compilation steps will help to illustrate how library code gets linked into an executable binary file. We first present the compilation steps and then discuss (with examples) different types of errors that can occur when compiling programs that use libraries.

C 编译器通过四个不同的步骤（外加一个在运行时进行的第五步），把 C 源文件（例如 myprog.c）翻译成可执行二进制文件（例如 a.out）。

The C compiler translates a C source file (e.g., myprog.c) into an executable binary file (e.g., a.out) in four distinct steps (plus a fifth step that occurs at runtime).

  1. 首先运行预编译步骤（precompiler step），展开预处理指令：即 C 程序中出现的 # 指令，例如 #define 和 #include。这一步的编译错误包括预处理指令中的语法错误，或者 gcc 找不到与 #include 指令对应的头文件。要查看预编译步骤的中间结果，可以给 gcc 传入 -E 标志（输出可以重定向到一个文件，用文本编辑器查看）：

  1. The precompiler step runs first and expands preprocessor directives: the # directives that appear in the C program, such as #define and #include. Compilation errors at this step include syntax errors in preprocessor directives or gcc not finding header files associated with #include directives. To view the intermediate results of the precompiler step, pass the -E flag to gcc (the output can be redirected to a file that can be viewed by a text editor):

  1. 接下来运行编译步骤（compile step），它完成编译任务的主体部分：把 C 程序源代码（myprog.c）翻译成特定于机器的汇编代码（myprog.s）。汇编代码是计算机可以执行的二进制机器码指令的人类可读形式。这一步的编译错误包括 C 语言语法错误、未定义符号警告，以及缺少定义和函数原型导致的错误。要查看编译步骤的中间结果，可以给 gcc 传入 -S 标志（这个选项会生成一个名为 myprog.s 的文本文件，内容是 myprog.c 翻译成的汇编代码，可以用文本编辑器查看）：

  1. The compile step runs next and does the bulk of the compilation task. It translates the C program source code (myprog.c) to machine-specific assembly code (myprog.s). Assembly code is a human-readable form of the binary machine code instructions that a computer can execute. Compilation errors at this step include C language syntax errors, undefined symbol warnings, and errors from missing definitions and function prototypes. To view the intermediate results of the compile step, pass the -S flag to gcc (this option creates a text file named myprog.s with the assembly translation of myprog.c, which can be viewed in a text editor):

  1. 汇编步骤（assembly step）把汇编代码转换为可重定位的二进制目标代码（myprog.o）。生成的目标文件包含机器码指令，但它不是一个可以单独运行的完整可执行程序。Unix 和 Linux 系统上的 gcc 编译器生成一种名为 ELF（Executable and Linkable Format，可执行与可链接格式）的特定格式的二进制文件。要在这一步之后停止编译，可以给 gcc 传入 -c 标志（这会生成一个名为 myprog.o 的文件）。二进制文件（例如 a.out 和 .o 文件）可以用 objdump 或类似的二进制文件查看工具来查看：

  1. The assembly step converts the assembly code into relocatable binary object code (myprog.o). The resulting object file contains machine code instructions, but it is not a complete executable program that can run on its own. The gcc compiler on Unix and Linux systems produces binary files in a specific format called ELF (Executable and Linkable Format). To stop compilation after this step, pass the -c flag to gcc (this produces a file named myprog.o). Binary files (e.g. a.out and .o files) can be viewed using objdump or similar tools for displaying binary files:

  1. 最后运行链接编辑步骤（link editing step），它用可重定位二进制文件（.o）和库（.a 或 .so）生成单个可执行文件（a.out）。在这一步中，链接器会核实 .o 文件中对名字（符号）的所有引用，都能在其他 .o、.a 或 .so 文件中找到。例如，链接器会在标准 C 库（libc.so）中找到 printf 函数。如果链接器找不到某个符号的定义，这一步就会失败，并报错说某个符号未定义。不带部分编译标志运行 gcc，会执行全部四个步骤，把 C 源代码文件（myprog.c）编译成可以运行的可执行二进制文件（a.out）：

    如果二进制可执行文件（a.out）静态链接了库代码（来自 .a 库文件），那么 gcc 会把 .a 文件中库函数的副本嵌入到生成的 a.out 文件中。应用程序对库函数的所有调用，都被绑定（bound）到 a.out 文件中库函数副本所在的位置。绑定是把一个名字与程序内存中的一个位置关联起来。例如，绑定对名为 gofish 的库函数的调用，就是把对这个函数名的使用替换为该函数在内存中的地址（后面的章节会更详细地讨论内存地址）。

    但如果 a.out 是通过动态链接库（来自共享目标库 .so 文件）生成的，那么 a.out 中就不包含这些库的库函数代码副本，而是包含一些信息，说明运行 a.out 需要哪些动态链接库。这样的可执行文件在运行时还需要一个额外的链接步骤。

  1. The link editing step runs last and creates a single executable file (a.out) from relocatable binaries (.o) and libraries (.a or .so). In this step, the linker verifies that any references to names (symbols) in a .o file are present in other .o, .a, or .so files. For example, the linker will find the printf function in the standard C library (libc.so). If the linker cannot find the definition of a symbol, this step fails with an error stating that a symbol is undefined. Running gcc without flags for partial compilation performs all four steps of compiling a C source code file (myprog.c) to an executable binary file (a.out) that can be run:

    If the binary executable file (a.out) statically links in library code (from .a library files), then gcc embeds copies of library functions from the .a file in the resulting a.out file. All calls to library functions by the application are bound to the locations in the a.out file to which the library function is copied. Binding associates a name with a location in the program memory. For example, binding a call to a library function named gofish means replacing the use of the function name with the address in memory of the function (in later chapters we discuss memory addresses in more detail.)

    If, however, the a.out was created by dynamically linking a library (from library shared object, .so, files), then a.out does not contain a copy of the library function code from these libraries. Instead, it contains information about which dynamically linked libraries are needed by the a.out file to run it. Such executables require an additional linking step at runtime.

  1. 如果 a.out 在链接编辑（第 4 步）时与共享目标文件链接，就需要运行时链接步骤（runtime linking step）。这种情况下，动态库代码（在 .so 文件中）必须在运行时加载并与正在运行的程序链接。这种在运行时加载和链接共享目标库的过程称为动态链接（dynamic linking）。当用户运行一个依赖共享目标的 a.out 可执行文件时，系统会在程序开始执行 main 函数之前完成动态链接。

    编译器在链接编辑这一编译步骤（第 4 步）中，把共享目标依赖信息加入 a.out 文件。程序开始执行时，动态链接器检查共享目标依赖列表，找到这些共享目标文件并把它们加载到正在运行的程序中。然后，它更新 a.out 文件中的重定位表项，把程序对共享目标中符号的使用（例如对库函数的调用）绑定到运行时加载的 .so 文件中这些符号的位置。如果动态链接器找不到可执行文件所需的某个共享目标（.so）文件，运行时链接就会报错。

    ldd 工具可以列出可执行文件所依赖的共享目标：

    GNU 调试器（GDB）可以检查正在运行的程序，显示在运行时加载和链接了哪些共享目标代码。我们会在第 3 章中介绍 GDB。不过，用于在运行时链接对动态链接库函数调用的过程查找表（Procedure Lookup Table，PLT），其检查细节超出了本教材的范围。

  1. The runtime linking step is needed if a.out was linked with shared object files during link editing (step 4). In such cases, the dynamic library code (in .so files) must be loaded at runtime and linked with the running program. This runtime loading and linking of shared object libraries is called dynamic linking. When a user runs an a.out executable with shared object dependencies, the system performs dynamic linking before the program begins executing its main function.

    The compiler adds information about shared object dependencies into the a.out file during the link editing compilation step (step 4). When the program starts executing, the dynamic linker examines the list of shared object dependencies and finds and loads the shared object files into the running program. It then updates relocation table entries in the a.out file, binding the program’s use of symbols in shared objects (such as calls to library functions) to their locations in the .so file loaded at runtime. Runtime linking reports errors if the dynamic linker cannot find a shared object (.so) file needed by the executable.

    The GNU debugger (GDB) can examine a running program and show which shared object code is loaded and linked at runtime. We cover GDB in Chapter 3. However, the details of examining the Procedure Lookup Table (PLT), which is used for runtime linking of calls to dynamically linked library functions, is beyond the scope of this textbook.

编译器会自动在标准目录位置中搜索头文件和库文件。例如，系统通常把标准头文件存放在 /usr/include，把库文件存放在 /usr/lib，gcc 会自动在这些目录中查找头文件和库；gcc 还会自动在当前工作目录中搜索头文件。
