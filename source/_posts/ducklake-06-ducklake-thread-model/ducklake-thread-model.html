关键不变量与常见误区

1两个池，每查询一条 lane

REGULAR 池（threads − 1 个后台 worker）跑计算 task，ASYNC 池（默认 min(4×核数, 256)）只做 I/O；REGULAR worker 空闲时也会顺手做 ASYNC 队列里的活。每个查询的 Executor 在两个队列里各有一条 lane（task_scheduler_type.hpp:15、task_scheduler.cpp:156）。

2轮转保证轮得到，不保证有 worker

worker 用 ConsumerToken 取 task，每条 lane 取满 16 个就整体换下一条（提交 0f67e73fd31）。但没有优先级、不抢占：后台 worker 默认 PROCESS_ALL，一个 task 跑完或阻塞才放手。

3调用线程也是执行者

每个活跃连接的调用线程循环取自己查询那条 lane 的 task（client_context_execution.cpp:349 → executor.cpp:444）。N 个并发连接 ≈ 后台 worker + N 条调用线程同时在跑；新查询就算 worker 全忙，也至少以并行度 1 推进。

4扫描按 row group 领活

DuckLake 的清单固定报 MULTIPLE_FILES，扫描直接起 threads 个 task。领活在 gstate.lock 下做 row_group_index++：文件 k 的 row group 全被领走才轮到 k+1，已领走的同时解码；read-ahead 在 ASYNC 池提前开文件、读列块。

5写：编码并行、追加串行

rotate=true 让 COPY 走 PARALLEL_COPY_TO_FILE：各线程并行 Prepare，在单文件锁下 Flush，多线程写同一个文件，超过 target_file_size 才换。带排序且未分区的表会退化成单线程 COPY；DELETE 的删除文件在 Finalize 里由一个线程逐个写。

6提交在调用线程上

COMMIT 经每事务一条的内部连接发一批 SQL，第一次不查冲突。撞主键后 sleep 退避（阻塞的是这条连接线程，不占 worker），比对 snapshot_changes 再用 snapshot_id+1 重写，最多 10 次；需要时用 TaskExecutor 并行重写删除文件——DuckLake 唯一自己投 task 的地方。

✕误区：文件清单在 planning 阶段就查好

不是。扫描所在 pipeline 被调度时（Pipeline::Schedule → Reset），才在 InitializeGlobalState 里单线程查一次 catalog（ducklake_multi_file_reader.cpp:288），源码注释说是为了避免 worker 一起挤在 GetFiles() 的锁上。

✕误区：等 I/O 时 worker 在干等

v2.0 把 Parquet 列块读取包装成 ASYNC 任务（parquet_reader.cpp:2488），扫描 task 返回 BLOCKED、Deschedule 让出线程，I/O 做完再被唤醒入队。inlined 表例外：它的元数据查询在持有扫描锁时同步执行。
