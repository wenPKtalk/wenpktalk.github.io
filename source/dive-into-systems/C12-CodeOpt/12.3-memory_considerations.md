## 12.3. 内存方面的考虑

*12.3. Memory Considerations*

程序员应当特别注意内存的使用，尤其是在使用矩阵和数组这类占用大量内存的数据结构时。尽管编译器提供了强大的优化功能，但编译器并不总能做出改善程序内存使用的优化。在本节中，我们用一个矩阵-向量程序的实现（[matrixVector.c](https://diveintosystems.org/book/C12-CodeOpt/_attachments/matrixVector.c)）来引导对改善内存使用的技术和工具的讨论。

> Programmers should pay special attention to memory use, especially when employing memory-intensive data structures such as matrices and arrays. Although compilers offer powerful optimization features, the compiler cannot always make optimizations that improve a program’s memory use. In this section, we use an implementation of a matrix-vector program ([matrixVector.c](https://diveintosystems.org/book/C12-CodeOpt/_attachments/matrixVector.c)) to guide discussion of techniques and tools for improving memory use.

这个程序的 `main` 函数执行两个步骤。首先，它分配并初始化输入矩阵、输入向量和输出矩阵。然后，它执行矩阵-向量乘法。在 10,000 × 10,000 的矩阵-向量规模上运行代码，可以看到 `matrixVectorMultiply` 函数占用了大部分时间：

> The `main` function of the program performs two steps. First, it allocates and initializes the input matrix, the input vector, and the output matrix. Next, it performs matrix-vector multiplication. Running the code on matrix-vector dimensions of 10,000 × 10,000 reveals that the `matrixVectorMultiply` function takes up the majority of the time:

```
$ gcc -o matrixVector matrixVector.c
$ ./matrixVector 10000 10000
Time to allocate and fill matrices: 1.2827
Time to allocate vector: 9.6e-05
Time to matrix-vector multiply: 1.98402
```

因此，我们的讨论将集中在 `matrixVectorMultiply` 函数上。

> Our discussion will thus focus on the `matrixVectorMultiply` function.

### 12.3.1. 循环交换

*12.3.1. Loop Interchange*

循环交换（loop interchange）优化交换嵌套循环中内外层循环的顺序，以最大化缓存局部性。编译器很难自动完成这项任务。GCC 中虽然有 `-floop-interchange` 编译选项，但目前默认不开启。因此，程序员最好留意自己的代码是如何访问数组和矩阵这类复合内存数据结构的。举个例子，我们来仔细看看 [matrixVector.c](https://diveintosystems.org/book/C12-CodeOpt/_attachments/matrixVector.c) 中的 `matrixVectorMultiply` 函数：

> Loop interchange optimizations switch the order of inner and outer loops in nested loops in order to maximize cache locality. Automatically performing this task is difficult for compilers to do. In GCC, the `-floop-interchange` compiler flag exists but is currently not available by default. Therefore, it is a good idea for programmers to pay attention to how their code is accessing memory-composite data structures like arrays and matrices. As an example, let’s take a closer look at the `matrixVectorMultiply` function in [matrixVector.c](https://diveintosystems.org/book/C12-CodeOpt/_attachments/matrixVector.c):

> **现代更新（截至 2026-11）· GCC 的循环交换**
> 按当前的 GCC 手册，`-O3` 会开启 `-floop-interchange`（手册的描述是：在 graphite 框架之外执行循环交换，可以改善循环嵌套的缓存性能，并让向量化等进一步的循环优化得以进行），`-O3` 同时还开启 `-floop-unroll-and-jam`、`-ftree-loop-distribution`（即本节后面讲的循环分裂）等相关的循环变换。不过，表 2 的数据说明，对本节这种由指针数组构成的「数组的数组」矩阵，编译器并没有替你把循环换过来，手动调整循环顺序依然必要。[GCC 手册：Optimize Options](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)

**表 1.** 对 `matrixVectorMultiply()` 函数进行循环交换

*Table 1. Loop interchange on the `matrixVectorMultiply()` function.*

**原始版本（matrixVector.c）**

> **Original Version (matrixVector.c)**

```
void matrixVectorMultiply(int **m,
                          int *v,
                          int **res,
                          int row,
                          int col) {
    int i, j;
    //cycles through every matrix column
    //in inner-most loop (inefficient)
    for (j = 0; j < col; j++){
        for (i = 0; i < row; i++){
            res[i][j] = m[i][j] * v[j];
        }
    }
}
```

**循环交换版本（matrixVector2.c）**

> **Loop interchange version (matrixVector2.c)**

```
void matrixVectorMultiply(int **m,
                          int *v,
                          int **res,
                          int row,
                          int col) {
    int i, j;
    //cycles through every row of matrix
    //in inner-most loop
    for (i = 0; i < row; i++){
        for (j = 0; j < col; j++){
            res[i][j] = m[i][j] * v[j];
        }
    }
}
```

输入矩阵和输出矩阵是动态分配的（C 语言章节讨论的第二种方法）。因此，矩阵的各行彼此不连续，而每一行中的元素是连续的。当前的循环顺序使程序逐列而不是逐行地遍历矩阵。回想一下，[数据是以*块*而不是元素为单位加载到缓存中的](../C11-MemHierarchy/11.4-caching.html)。因此，当访问 `res` 或 `m` 中某个数组的元素 *x* 时，*与 x 相邻的元素*也会被加载到缓存中。逐「列」遍历矩阵会导致更多的缓存未命中，因为每次访问都迫使缓存加载新的块。[表 2](12.3-memory_considerations.html) 显示，加上优化选项并没有缩短这个函数的运行时间。然而，只要交换一下循环的顺序（如前面的代码示例以及 [matrixVector2.c](https://diveintosystems.org/book/C12-CodeOpt/_attachments/matrixVector2.c) 所示），函数就能快将近八倍，并让编译器能够进行更多的优化。

> The input and output matrices are dynamically allocated (second method discussed in C chapter). As a result, the rows in the matrices are not contiguous to one another, whereas the elements in every row are contiguous. The current ordering of the loops causes the program to cycle through each column instead of every row. Recall that [data is loaded into cache in *blocks*](../C11-MemHierarchy/11.4-caching.html) not elements. As a result, when an element *x* in an array in either `res` or `m` is accessed, the *elements adjacent to x* are also loaded into cache. Cycling through every "column" of the matrix causes more cache misses, as the cache is forced to load new blocks with every access. [Table 2](12.3-memory_considerations.html) shows that adding optimization flags does not decrease the runtime of the function. However, simply switching the order of the loops (as shown in the previous code examples and in [matrixVector2.c](https://diveintosystems.org/book/C12-CodeOpt/_attachments/matrixVector2.c)) makes the function nearly eight times faster and allows the compiler to perform additional optimizations.

> The Valgrind tool `cachegrind` (discussed in [Chapter 11](../C11-MemHierarchy/11.5-cachegrind.html)) is a great way to identify data locality issues, and reveals the cache access differences in the two versions of the `matrixVectorMultiply` function shown in the previous example.

### 其他几种改善局部性的编译器优化：循环分裂与循环融合

*12.3.2. Some Other Compiler Optimizations for Improving Locality: Fission and Fusion*

在 10,000 × 10,000 个元素上重新运行改进后的程序，得到下面的运行时间：

> Rerunning the improved program on 10,000 × 10,000 elements yields the following runtime numbers:

```
$ gcc -o matrixVector2 matrixVector2.c
$ ./matrixVector2 10000 10000
Time to allocate and fill matrices: 1.29203
Time to allocate vector: 0.000107
Time to matrix-vector multiply: 0.271369
```

现在，分配和填充矩阵所花的时间最多。进一步的计时表明，实际上最耗时的是填充矩阵。我们来仔细看看那段代码：

> Now, matrix allocation and filling takes the most time. Additional timing reveals that it is the filling of the matrices that in fact takes the most time. Let’s take a closer look at that code:

```
//fill matrices
for (i = 0; i < rows; i++){
    fillArrayRandom(matrix[i], cols);
    fillArrayZeros(result[i], cols);
}
```

为了填充输入矩阵和输出矩阵，一个 `for` 循环遍历所有行，并对每个矩阵调用 `fillArrayRandom` 和 `fillArrayZeros` 函数。在某些情况下，编译器把单个循环拆成两个独立的循环可能会更有利（称为**循环分裂**，loop fission），如[表 3](12.3-memory_considerations.html) 所示。

> To fill the input and output matrices, a `for` loop cycles through all the rows, and calls the `fillArrayRandom` and `fillArrayZeros` functions on each matrix. In some scenarios, it may be advantageous for the compiler to split the single loop into two separate loops (known as **loop fission**), as shown in [Table 3](12.3-memory_considerations.html).

**表 3.** 对 `main` 中填充矩阵的 for 循环进行循环分裂的示例

*Table 3. Loop fission example on fill matrices for loop in `main`.*

**原始版本**

> **Original Version**

```
for (i = 0; i < rows; i++) {
    fillArrayRandom(matrix[i], cols);
    fillArrayZeros(result[i], cols);
}
```

**循环分裂后**

> **With loop fission**

```
for (i = 0; i < rows; i++) {
    fillArrayRandom(matrix[i], cols);
}

for (i = 0; i < rows; i++) {
    fillArrayZeros(result[i], cols);
}
```

把在同一范围上运行的两个循环的内容合并到一个循环中（即循环分裂的逆过程），称为**循环融合**（loop fusion）。循环分裂和循环融合都是编译器为改善数据局部性而可能执行的优化。面向多核处理器的编译器也可能利用循环分裂或融合，让循环能在多个核心上高效执行。例如，编译器可能用循环分裂把两个循环分配给不同的核心。同样，编译器可能用循环融合把相互依赖的操作合并到循环体中，再把循环迭代的一个子集分配给每个核心（假设各次迭代之间的数据是独立的）。

> The process of taking two loops that operate over the same range and combining their contents into a single loop (i.e., the opposite of loop fission) is called **loop fusion**. Loop fission and fusion are examples of optimizations a compiler might perform to try to improve data locality. Compilers for multicore processors may also use loop fission or fusion to enable loops to execute efficiently on multiple cores. For example, a compiler may use loop fission to assign two loops to different cores. Likewise, a compiler may use loop fusion to combine together dependent operations into the body of the loop and distribute to each core a subset of the loop iterations (assuming data between iterations are independent).

在我们的例子中，手动应用循环分裂并不能直接提高程序性能；填充数组所需的时间几乎没有变化。不过，它可能会让一个更隐蔽的优化显现出来：包含 `fillArrayZeros` 的那个循环是不必要的。`matrixVectorMultiply` 函数会给 `result` 数组中的每个元素赋值，事先把它们全部初始化为零是多余的。

> In our case, applying loop fission manually does not directly improve program performance; there is virtually no change in the amount of time required to fill the array. However, it may make clear a more subtle optimization: the loop containing `fillArrayZeros` is not necessary. The `matrixVectorMultiply` function assigns values to each element in the `result` array; a prior initialization to all zeros is unnecessary.

**表 4.** 去掉对 `fillArrayZeros` 的多余调用

*Table 4. Removing unneeded call to `fillArrayZeros`.*

### 12.3.3. 用 Massif 进行内存剖析

*12.3.3. Memory Profiling with Massif*

做了上面的改动之后，运行时间只略有下降。尽管它省去了把结果矩阵所有元素填充为零的步骤，但用随机数填充输入矩阵仍需要相当多的时间：

> Making the previous change results in only a slight decrease in runtime. Although it eliminates the step of filling in all elements in the result matrix with zeros, a significant amount of time is still required to fill the input matrix with random numbers:

```
$ gcc -o matrixVector3 matrixVector3.c
$ ./matrixVector3 10000 10000
Time to allocate matrices: 0.049073
Time to fill matrices: 0.946801
Time to allocate vector: 9.3e-05
Time to matrix-vector multiply: 0.359525
```

尽管各个数组在内存中并不连续存放，但每个数组都占 10,000 × `sizeof(int)` 字节，即 40,000 字节。由于总共分配了 20,000 个数组（初始矩阵和结果矩阵各 10,000 个），这相当于 8 亿字节，即大约 762 MB 的空间。用随机数填满 762 MB 的空间，花很多时间也就不难理解了。对于矩阵，内存使用量随输入规模呈平方增长，可能对性能产生很大影响。

> Even though each array is stored noncontiguously in memory, each one takes up 10,000 × `sizeof(int)` bytes, or 40,000 bytes. Because there is a total of 20,000 (10,000 each for the initial matrix and the result matrix) arrays allocated, this corresponds to 800 million bytes, or roughly 762 MB of space. Filling 762 MB with random numbers understandably takes a lot of time. With matrices, memory use increases quadratically with the input size, and can play a large role in performance.

Valgrind 的 `massif` 工具可以帮助你剖析内存使用情况。与本书介绍过的其他 Valgrind 工具（[memcheck](../C3-C_debug/3.3-valgrind.html)、[cachegrind](../C11-MemHierarchy/11.5-cachegrind.html) 和 [callgrind](12.1-basic.html)）一样，`massif` 作为程序可执行文件的包装器运行。具体来说，`massif` 在程序运行过程中给程序的内存使用拍快照，剖析内存使用量如何波动。程序员可能会发现 `massif` 工具很适合用来跟踪程序如何使用堆内存，以及找出改善内存使用的机会。我们在 `matrixVector3` 可执行文件上运行 `massif` 工具：

> Valgrind’s `massif` tool can help you profile memory use. Specifically, `massif` takes snapshots of program memory use throughout the program, and profiles how memory usage fluctuates. Programmers may find the `massif` tool useful for tracking how their programs use heap memory, and for identifying opportunities to improve memory use.
